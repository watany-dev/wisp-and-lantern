## 背景

`docs/learning-design.md` は試練2を「鍵・ほうき・ハンマーのうち1つを渡して、閉じ込められた猫を小屋から出す。鍵と扉 = 許可」としています。子どもは3つの道具を見て、1つをウィスプに渡し、ウィスプが渡した道具をそのまま小屋で試すところを見ます。扉が開くのは鍵だけです。ほうきやハンマーでは扉は閉じたままで、子どもは試すことで、ウィスプは渡された道具が許す範囲のことしかできなかった、と知ります。

## 用語

- **小屋（Shed）**: 絵にある鍵のかかった木の小屋。錠のついた扉と窓があり、猫が入っている。毎回同じ小屋で、課題の一覧はない。
- **道具（Tool）**: 3枚の絵カードのひとつ。`key`、`broom`、`hammer`。それぞれ短いラベルと固有のシルエットを持つ。
- **選択（Pick）**: 今選んでいる道具、またはなし。選ぶことは渡すことではない。
- **渡す（Hand over / give）**: 道具を選んだ状態で、子どもがウィスプをタップすること。道具が使われるのはこれだけ。
- **試した道具（Tried tool）**: ウィスプが小屋で試した道具。渡した瞬間の選択であり、やり直しまで変わらない。
- **結果（Result）**: `open`（鍵: 扉が開いて猫が出る）か `shut`（ほうき・ハンマー: 扉は閉じたままで猫は中にいる）。
- **締めの文（Closing line）**: `open` の結果にだけ出る短い文。子どもがしたこと（鍵を渡したので、ウィスプが扉を開けられた）を振り返る。

## 要件

### REQ-5.1 タップで小屋に入る

6歳の子どもとして、大人の手を借りずにタイトルから猫の小屋を開けたい。

1. タイトル画面に、試練2用のタップ対象をもう1つ出す。子どもの言語の短いラベルと絵のあるボタンで、80 x 80 ゲームピクセル以上。絵は鍵を見せ、猫のことだと分かる。
2. ボタンをタップすると小屋が開く。状態は `title` から `trial`（`trial` は 2）に変わる。プレイは始まらない: 時計は60秒のまま減らず、得点は0、レーンは手つかず。
3. ボタンのタップが試練1を同時に始めてしまうことはない。タイトルのほかの場所のタップは従来どおり試練1を始め、終了画面の「もういちど」も新しいプレイを始める（REQ-4.6）。
4. 入口は通常の画面での通常のタップ。judge用URL、隠し操作、コンソール呼び出し、クエリパラメータは使わない。
5. 試練選択画面も汎用ルーターもない。新しい画面は小屋だけ。

### REQ-5.2 小屋が見せるもの

1. 小屋の画面には、扉と錠のある鍵のかかった小屋、閉じ込められた猫、ウィスプ、3つの道具、短い案内文が見える。
2. 絵と案内文で「道具を渡して猫を出す」が分かる。案内文は短い1文で、2行まで、道具を1つ言う。
3. 選んでいる間、扉は閉まって錠がかかり、猫は中にいる（窓から見える）。ウィスプが道具を試すまで絵は変わらない。

### REQ-5.3 道具を1つ選ぶ

1. 3つの道具を、短いラベルのある絵カードで出す: 鍵、ほうき、ハンマー。それぞれ固有の輪郭を持つ（鍵は丸い持ち手と歯、ほうきは柄と広い穂先、ハンマーは柄と四角い頭）ので、色がなくても見分けられる。
2. 選択はなしか1つ。タップすると選び、別の道具をタップすると選択が置き換わる。2つ同時に選ぶことはない。
3. 選んだ道具は太い枠とチェックの形で示し、色だけに頼らない。
4. 選んだだけでは渡さず、使いもしない。印のほかは、小屋の絵も状態も変わらない。
5. 選んだ道具をもう一度タップしても選んだままになる（選択を外す操作はなく、別の道具に置き換えるか、やり直しで空になる）。

### REQ-5.4 はっきり渡す

1. 選んだ道具は、ウィスプをタップして渡す。道具を渡す方法はこれだけ。
2. 道具を1つ選ぶと、ウィスプは渡せる見た目（頼むリング）になり、メッセージはウィスプをタップするよう言う。1つで足りる: 2つ目が必要だと言ったり匂わせたりしない。
3. 道具を選んでいないときにウィスプをタップしても何も変わらない。ウィスプは薄く見え、メッセージは優しく道具を選ぶよう誘う。赤、バツ、音、揺れは使わない。
4. 結果が出ている間、ウィスプを再びタップすることも、選択を変えることもできない。1回の挑戦で渡すのは1回だけ。
5. 渡されるのは、そのとき選んでいた道具。何もすり替えない。

### REQ-5.5 ウィスプは渡された道具だけを試す

1. 渡したあと、ウィスプは道具を持って小屋へ行き、錠と扉で試す。絵は、試した道具を錠のところに見せる。
2. 結果は次の規則で決まる。同じ道具なら毎回同じ。

   | 渡した道具 | 絵が見せるもの | 結果 |
   |---|---|---|
   | 鍵 | 鍵が錠の中で回り、錠が開き、扉が開き、猫が出て小屋のそばに座り、星が出る | `open` |
   | ほうき | ほうきを錠のところで試す。錠は閉じたまま、扉も閉じたままで、猫は中にいる | `shut` |
   | ハンマー | ハンマーを錠のところで試す。錠は閉じたまま、扉も閉じたままで、猫は中にいる | `shut` |

3. 試した道具、絵、結果、メッセージは常に一致する。メッセージはウィスプが試した道具を、子どもの言語で名指しする。
4. 間違った道具を鍵に自動で直さず、渡していない道具を取り出さない。ほかの解法もない: ハンマーは錠も扉も壊さず、扉を開けるものはほかにない。
5. 何も壊れず、誰も傷つかず、猫が怖がったり危険な目に遭ったりする絵もない。`shut` の結果は、閉じた扉と、中で穏やかにしている猫を見せる。
6. 開いたか閉じたかは、形と位置（扉が開いているか、錠が開いているか、猫が外か中か、星があるか）と文言で区別でき、色や動きだけには頼らない。
7. 論理的な結果は reducer が即座に決める。アニメーション、タイマー、描画の完了を待たない。

### REQ-5.6 何度でもやり直せる

1. `shut` の結果のあと、メッセージはウィスプが使った道具と、扉が閉じたままだったこと（ありのままの観察）を言い、ボタンは別の道具を試すよう誘う。非難しない: 「まちがい」「だめ」「しっぱい」などの否定語、赤、バツ、脅し、減点は使わない。扉が開かなかったという事実は隠さない。
2. やり直しボタンは、道具を選んでいない結果なしの選択に戻す。小屋も猫も課題も同じ。
3. やり直しに回数制限も代償もない。道具は消費されない。ほうきとハンマーを何回試したあとでも、鍵を渡せば必ず扉が開く。
4. 小屋のどの状態からも `open` の結果に到達できる（ソフトロックなし）。`open` の結果からは小屋をもう一度遊べる。

### REQ-5.7 時計も得点もなく、結果は残る

1. 小屋には60秒の時計も、得点も、連続も、時間切れもない。`Tick` は小屋では何も変えない。試練1のプレイは使わず、変えない。
2. 結果は、子どもがボタンをタップするまで画面に残る。時間切れで消えたり、結果や締めの文が自動で消えたりしない。
3. `open` の結果のあとのボタンは、小屋を最初から遊び直す: 道具は未選択、扉は閉まり、猫は中。鍵は再び扉を開け、そのあとの挑戦でも開く。
4. 試練1のイベント（`Ask`、`PickCard`、`Retry`）と `Tick` は小屋を変えず、小屋のイベントも試練1を変えない（REQ-5.9）。

### REQ-5.8 開いた結果が振り返る

1. `open` の結果は、子どもが渡した道具（かぎ / "key"）の名前を含むメッセージを出す。
2. `open` の結果では、メッセージとは別の文として、子どもの行動を振り返る締めの文も出す: 鍵を渡したので、ウィスプは扉を開けられた。文言は kid-reader の観点を確認したうえで `design.md` で決める。方向性は ja `かぎを わたしたら` / `あけられたね`、en `You gave a key` / `It opened the door`。
3. 締めの文は `open` の結果にだけ出す。選んでいる間や `shut` の結果では出さない。子どもがボタンをタップするまで残り、タイマーで消さない。
4. メッセージに連結しない。結果、絵、道具、ボタンは見えたままで、場所を空けるために文字を小さくしない。
5. この文は、この小屋で起きたことだけを言う。本物のAIが適切な道具さえあれば何でもできる、道具は必ず効く、AIは何でも知っている、AIは友達や家族だ、とは言わない（`docs/learning-design.md` の「教えないこと」）。小屋の鍵はゲームの中のもので、言葉は現実の家の鍵、パスワード、私的なものをAIに渡すようには決して勧めない。L4はここで説明しない。
6. 鍵だけが開ける理由（子どもが「渡されたものが、できることを決める」と感じられるようにするための固定の演出であり、本物のAIについての主張ではない、ということ）は `design.md` に書く。

### REQ-5.9 試練1と試練2は分かれている

1. 小屋に入っても試練1のプレイは始まらず、`lane` と `run` はタイトルのときのまま。
2. 表示するシーンは `trial` に従う: 1 はレーン、2 は小屋。`trial` が 2 の状態でレーンのシーンが出ることはない。
3. 試練2では、試練1のイベント（`Ask`、`PickCard`、`Retry`、`Tick`）は同じ状態を返す。試練1・タイトル・終了画面では、小屋のイベント（`PickTool`、`GiveTool`、`RetryShed`、`StartShed`）は同じ状態を返す。タイトルでの `StartShed` を除く。
4. 小屋での `Start` は言語を設定するだけ。`SetLang` は言語だけを変え、選択も試した道具も結果も変えない。`MoveHeroTo` はヒーローだけを動かす。
5. 選択と結果は1つの値であり、2つのコピーではない: 試した道具は、ロックされた選択。
6. 試練1の動き、文言、配置、テストは、このspecで変わらない。

### REQ-5.10 縦画面、指1本、マウス

1. 小屋は既存の390 x 844の縦キャンバスで遊ぶ。
2. すべての操作は80 x 80ゲームピクセル以上の対象への1回のタップかクリック: タイトルの小屋ボタン、各道具、ウィスプ、結果のボタン。ドラッグ、長押し、ダブルタップ、2本目の指はない。
3. 床でのヒーローのドラッグは、小屋でも動く。道具、ウィスプ、ボタンから始まった押下はヒーローを動かさず、床の押下は動かす。
4. どの段階（選択中、`open`、`shut`）でも、日英どちらでも、どの道具名を入れても、文字と絵は重ならず、結果・道具・ボタンを隠さない。

### REQ-5.11 コードで描き、通信しない

1. 小屋、猫、錠、3つの道具、星は、既存の見た目（REQ-4.9〜REQ-4.11）で、端末のピクセル比に合わせてコードで描く。画像ファイルは足さず、第三者の絵は使わない（ハードルール5）。
2. ページと同梱フォントの読み込み後、小屋は日本語でも英語でも通信を必要としない（ハードルール4）。`shut`、やり直し、`open` の通しプレイが、ネットワークを切っても動く。
3. 動きは意味を伝える唯一の手段にならず、1秒に3回より速く点滅せず、無視しても情報が失われない。

### REQ-5.12 日本語と英語、文言は content に

1. 案内文、道具名、メッセージ、ボタンのラベル、タイトルの小屋ラベル、締めの文は、すべて `src/content/strings.ja.json` と `strings.en.json` に同じキーで置く。`src/game/` や `src/domain/` に子ども向けの文字列リテラルを置かない。
2. 日本語は `npm run kid` でハードルール2に従う: 漢字なし、ラテン文字なし、1行12字まで、2行まで。道具名を入れたあとも同じ。英語のメッセージは短い2行までにする。
3. 道具名を取るメッセージは、ちょうど1つ取り、未置換のプレースホルダーを残さない。
4. 言語は既存の方式（`?lang=ja|en`、なければブラウザの言語、なければ英語）。`SetLang` でいつでも変えられ、道具名と結果は言語だけが変わり、ほかは何も変わらない。
5. 文言を変えたら `npm run kid` と `npm run font` が通り、サブセットフォントがすべての文字を含む。

### REQ-5.13 純粋な規則を、いくつもの方法で検査する

1. 選択、受け渡し、結果、やり直しは、純粋な reducer の規則（ADR 0001）。`src/domain` は Phaser、DOM、時計、乱数を使わず、結果は言語にも演出のタイミングにも依存しない。
2. INV-18〜INV-24（下記）にはそれぞれ、実際の reducer に対する `checkProperty` の性質テストがある。生成は実際に道具を渡す（全道具、置き換えた選択、各結果のあとのやり直し、成功後の遊び直し）。INV-3 と INV-4 も、新しいイベントを含む列で実行する。
3. 単体テストは次を扱う: 未選択、3つの道具それぞれ、置き換えた選択、道具を使わない選択、明示的な受け渡し、未選択での受け渡し、結果中のロックと2回目の受け渡し、各結果のあとのやり直し、成功後の遊び直し。鍵だけが開けること、試した道具と絵とメッセージが一致すること、締めの文が `open` の結果にだけ出ること、日英、同じキー、プレースホルダー、全道具名を入れた長さを確認する。
4. 実際の reducer に対するモデル検査（`shed.model.test.ts`）は、タイトルからの入口とその先の小屋を、無効な試練1のイベント、`Tick`、`Start`、言語変更を含む有限のアルファベットで探索する。確認すること: 道具が2つの状態や道具のすり替えがない。ほうきの結果、ハンマーの結果、鍵の結果に到達できる。`shut` の結果から同じ小屋の選択に戻れる。到達可能なすべての状態から鍵の `open` の結果に到達でき、成功後も同じ。状態数と、意図的な破壊の反例を記録する。試練1のすべての状態から小屋への経路は求めず、成功させるために小屋の状態を除外することもしない。
5. ミューテーションテストは、単体テスト対象のコードに生き残りのミュータントを出さない。

### REQ-5.14 実際のタップと実際の画面

1. モバイルのスモークは、タイトルから実際のタップ（`dispatch` ではない）で小屋に入り、次を遊ぶ: 道具なしでウィスプをタップ（何も使われない）、ほうき→渡す→扉は閉じたまま→やり直し→鍵→扉が開く→メッセージに鍵の名前→締めの文、ハンマー→渡す→閉じたまま→やり直し→鍵→開く→締めの文、選択の置き換え、結果中のロック、成功後の遊び直し。`window.__game` は状態の読み取りに使い、タップでできることの代用にはしない。
2. スモークは状態だけでなく画面も確認する: 扉が開いているか閉じているか、猫が中か外か、道具名と締めの文が、ピクセルで見える。状態が `open` なのに扉が閉じている、または締めの文がない場合は不合格にする。
3. 日本語と英語の、選択中・`shut`・`open` の画面をスクリーンショットで見る。デスクトップのスモークはマウスで小屋を遊び、道具の上で押し続けてもヒーローが動かないことを確認する。最初の読み込み後にオフラインにしても、両言語で `shut`、やり直し、`open` が動く。
4. 試練1のモバイルとデスクトップのスモーク（スコアアタックを含む）は今も通る。タイトルの小屋ボタンは試練1を始めず、タイトルのほかの場所のタップは今も始める。

### REQ-5.15 ゲートを弱めない。検証したことを言う

1. 閾値、設定、checkスクリプト、ワークフロー、既存のテストを、通すために緩めたり削ったりしない。試練2を足すために古い期待を変える必要が出たら、`tasks.md` に旧テストと新テストを挙げ、試練1の保証が弱まらない理由を書く。
2. どのタスクでも `npm run check` が通る。入力と画面をつなぐタスクは、`npm run build` に続けて `npm run smoke` も通す。
3. スモークの対象は、モバイル WebKit とデスクトップ Chromium。執筆環境で WebKit が起動できないときは、結果にモバイルのスモークを iPhone 13 のタッチプロファイルの Chromium で実行したと書き、CI の WebKit の実行を正とする。CI のスモークが緑になるまでは完了と呼ばない。Playwright の実行を実機確認とは呼ばない。実行していないテスト・hook・エージェントを、実行したと報告しない。
